### Opening statements

**DEFENCE — opening statement**

WebSockets are indispensable for this real‑time collaborative UI because they provide a true bidirectional, low‑latency channel that eliminates the per‑message overhead of HTTP polling or server‑sent events, enabling instant propagation of edits and cursor positions to all participants.  The persistent socket connection allows the server to push updates as soon as state changes occur, which is critical for maintaining a consistent shared view when dozens or hundreds of users are simultaneously interacting; this level of immediacy cannot be reliably achieved with one‑way or interval‑based HTTP techniques that introduce noticeable jitter and increased bandwidth usage.  Modern load balancers (NGINX, HAProxy, AWS ALB) natively support WebSocket traffic through sticky sessions or path‑based routing, meaning the scaling complexity is manageable and can be integrated into existing infrastructure without a rewrite of client logic or deployment pipelines.  Robust reconnection strategies—such as exponential backoff with state synchronization on reconnect—ensure resilience across flaky networks, guaranteeing that transient disconnects do not break the collaborative experience.  The operational burden added by WebSocket management is a necessary trade‑off for delivering the real‑time responsiveness required by the application’s core use cases.

_Key points:_
- True bidirectional low‑latency channel
- Eliminates HTTP overhead per update
- Immediate push of state changes
- Supports high concurrent user scaling via sticky load balancing
- Resilient reconnection mechanisms
- Operational trade‑offs justified by performance requirements


**PROSECUTION — opening statement**

The Prosecution submits that server-sent events (SSE) or smart polling are the most suitable choices for delivering live updates in a real-time collaborative UI, despite their unidirectional nature. These methods offer unparalleled simplicity, as they leverage plain HTTP, which is widely supported and integrates effortlessly with existing infrastructure, including proxies. This compatibility ensures that no additional setup is required, reducing potential bottlenecks and errors during deployment. Furthermore, load balancing becomes less complex because traditional HTTP mechanisms can be employed without the need for specialized handling, ensuring scalability is not compromised. While it is true that SSEs are unidirectional and less efficient for high-frequency updates, their advantages in terms of ease of implementation, compatibility, and reduced operational complexity make them a preferable choice that balances cost-effectiveness with practicality.

These techniques collectively eliminate the dependency on Redis Streams while still offering stateful session recovery, minimal reconnection latency, and seamless load balancing across a cluster of stateless worker pods.
