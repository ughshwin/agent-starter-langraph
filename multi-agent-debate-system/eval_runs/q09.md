## Q9: A microservices platform must standardise how it verifies auth tokens between services. Should it use stateless JWTs (no per-request lookup, scales trivially, but hard to revoke before expiry and awkward to carry fine-grained permissions), or server-side sessions / token introspection (instant revocation and central control, at the cost of a lookup/dependency on every request)?

- **Defence position:** The platform must use stateless JWTs to ensure trivial scalability and eliminate per-request dependencies, despite challenges in token revocation and fine-grained permission management.
- **Prosecution position:** The platform must adopt server-side session management or token introspection to enable instant token revocation and centralized control, even at the cost of introducing per-request lookups and potential scalability trade-offs.

### Opening statements

**DEFENCE — opening statement**

Stateless JSON Web Tokens (JWTs) provide the only viable path to true horizontal scalability for a distributed microservices platform; each service can validate a token locally with a shared public key, eliminating expensive cross-service lookups and allowing independent auto‑scaling without a central session store.  The removal of per-request dependency on a stateful datastore removes a single point of failure, reduces network latency by orders of magnitude, and cuts operational overhead—no clustered cache or replicated database is needed to keep token metadata in sync across shards.  While revocation is indeed a technical challenge, it can be addressed through short token lifetimes (e.g., one‑minute windows), rotating signing keys, and optional distributed blacklist checks that are performed only for tokens flagged as revoked; the added latency is negligible compared with the cost of maintaining a global session table.  Fine‑grained permission control remains fully achievable by embedding scopes, roles, or attribute claims directly within the JWT payload—these assertions are cryptographically protected and can be updated simply by issuing new tokens, avoiding the complexity of per-request database joins to an ACL system.

_Key points:_
- Trivial horizontal scalability via local signature verification
- Fault‑tolerant design with no single point of failure
- Cost savings from eliminating shared session stores
- Secure short‑lived tokens mitigated by key rotation and optional revocation lists
- Fine‑grained permissions encoded directly in JWT claims


**PROSECUTION — opening statement**

The platform must adopt server-side session management or token introspection to enable instant token revocation and centralized control, even at the cost of introducing per-request lookups and potential scalability trade-offs. This approach ensures robust security by allowing immediate invalidation of compromised tokens, maintaining consistent access policies across services through centralized control, and supporting fine-grained permission management. While stateless JWTs offer scalability without lookups, they lack the critical ability to revoke tokens promptly and manage permissions effectively, which are paramount for a secure microservices architecture.

_Key points:_
- Instant token revocation capability is essential for security.
- Centralized control ensures consistent access policies across services.
- Fine-grained permission management is more efficient with server-side solutions.
- Scalability concerns are manageable and secondary to security benefits.

### Closing statements

**DEFENCE — closing statement**

In conclusion, the evidence overwhelmingly supports adopting stateless JWTs for our microservices platform because they deliver true horizontal scalability by removing per‑request lookups and dependency on a central session store; each service can validate tokens locally with negligible latency while scaling independently without network coordination. Short token lifetimes (5–15 minutes) combined with automated HSM‑backed key rotation, JWKS caching via CDN, and graceful key‑versioning ensure that even if the signing infrastructure is temporarily unavailable, all services continue to reject compromised or stale tokens within a bounded window—thereby preserving security without introducing downtime. Fine‑grained permission control remains fully attainable through claim embedding; versioned claims and a shared policy library eliminate the need for database joins or per‑request ACL checks, while still allowing dynamic updates via token re‑issuance. In contrast, server‑side sessions impose costly network round‑trips, create single points of failure, increase operational overhead, and expose the platform to scalability bottlenecks that JWTs intrinsically avoid.

_Key points:_
- Stateless JWTs enable true horizontal scaling by eliminating per‑request lookups
- Short lifetimes + HSM key rotation keep revocation risks bounded even during infrastructure outages
- Fine‑grained permissions are encoded in claims, avoiding database joins or ACL engines
- Server‑side sessions introduce latency, complexity, and single points of failure absent from JWTs


**PROSECUTION — closing statement**

In conclusion, the evidence strongly supports adopting server-side session management or token introspection because it ensures robust security through instant token revocation and centralized control. While stateless JWTs offer scalability without lookups, they lack the critical ability to revoke tokens promptly and manage permissions effectively. Server-side sessions provide a secure architecture by allowing immediate invalidation of compromised tokens and maintaining consistent access policies across services. Despite scalability trade-offs, the benefits of security and control are paramount for a reliable microservices platform.

_Key points:_
- Instant revocation capability is irreplaceable for critical security needs.
- Centralized control ensures uniform enforcement of policies across services.
- Scalability trade-offs are outweighed by the need for robust security measures.
- Server-side sessions provide a secure architecture that stateless JWTs cannot match.
